Завершённость, атомарность/единичность, непротиворечивость, недвусмысленность, выполнимость, обязательность/актуальность, прослеживаемость, модифицируемость, проранжированность, корректность/проверяемость; плюс правила набора (отсутствие противоречий и дублирования, структурированность, полнота).

## Подтверждённые находки и принятые решения

### 1. 🔴 HIGH — `4.3.1 (буллет «Создание/реактивация связи и инициализация абонемента»)`
*Свойство:* Атомарность/единичность (Atomicity)

**Нарушение.** Подтверждено по тексту: один буллет действительно содержит четыре независимо проверяемых условия — «если строки нет — создать», «если removed_at IS NOT NULL — реактивировать сбросом removed_at», «если активна — без изменений», плюс «инициализация строки memberships ... с remaining_visits = 0, если её ещё нет». Каждое — отдельная входная ситуация с отдельным ожидаемым результатом и отдельным тест-кейсом (создание vs. реактивация vs. no-op vs. инициализация счётчика). Это классическое нарушение атомарности: на один буллет нельзя написать один тест. Смягчающее: семантика частично продублирована в 5.3 и 4.4.1, но требование в 4.3.1 остаётся склеенным.

**Исправление.** Разбить буллет на отдельные нумерованные подпункты с собственными критериями приёмки: 4.3.1.a — при отсутствии строки coach_athlete создаётся новая активная связь (created_at = now(), removed_at = NULL); 4.3.1.b — при removed_at IS NOT NULL связь реактивируется сбросом removed_at в той же строке; 4.3.1.c — при уже активной связи (removed_at IS NULL) изменений в coach_athlete не вносится (no-op); 4.3.1.d — при отсутствии строки memberships пары она создаётся с remaining_visits = 0, существующая строка не трогается. Каждое — с явным ожидаемым результатом.

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 2. 🔴 HIGH — `4.3.4 + 5.5 + 4.3.1 + 6.2 (RPC) + 9.1 R5 + 8.1.1`
*Свойство:* Выполнимость (Feasibility)

**Нарушение.** Подтверждено по тексту. Спека определяет инвариант уникальности через сырой предикат: partial unique index `unique(coach_id, athlete_id) where ended_at is null` (5.5 стр.525; 4.3.1 стр.222). Одновременно авто-завершение делается ТОЛЬКО расчётом на лету: 'для MVP достаточно расчёта на лету... отдельный pg_cron для материализации ended_at... необязателен в v1' (4.3.4 стр.245; продублировано в 6.2 стр.666 и 8.1.1 стр.769). Поэтому ended_at у зависшей сессии физически остаётся NULL. RPC чек-ина в 6.2 (стр.654-660) НЕ закрывает просроченную сессию перед INSERT — он лишь 'проверка нет активной сессии по паре (опора на unique(...) where ended_at is null)' и затем INSERT. Значит при повторном чек-ине той же пары на следующий день INSERT с ended_at IS NULL нарушит частичный уникальный индекс, либо по правилу 4.3.1 (стр.222) пользователю покажут 'тренировка уже идёт' для вчерашней висящей сессии. Без обязательной материализации повторный чек-ин у того же тренера блокируется до ручного завершения — это реальная нереализуемость заявленной ключевой функции. Частичный индекс действительно не умеет выразить временной предикат с now(), так что 'активна = ended_at IS NULL' и 'активна = в пределах 2ч' расходятся.

**Исправление.** Устранить рассинхрон двух определений 'активной сессии'. Рекомендуемый вариант (минимальные изменения, без обязательного pg_cron): в RPC чек-ина (6.2) ПЕРЕД проверкой/INSERT в той же транзакции под FOR UPDATE закрывать собственную просроченную сессию пары: UPDATE visits SET ended_at = started_at + interval '2 hours', end_reason='auto' WHERE coach_id=:c AND athlete_id=:a AND ended_at IS NULL AND started_at <= now() - interval '2 hours'. Это снимает частичный уникальный индекс с вчерашней сессии до INSERT и сохраняет инвариант 'не более одной активной на пару'. Частичный уникальный индекс при этом можно оставить как есть (он корректно работает, т.к. просроченные сессии материализуются точечно в момент чек-ина). Альтернатива — сделать pg_cron-материализацию авто-завершения ОБЯЗАТЕЛЬНОЙ в v1 (убрать формулировку 'необязателен' из 4.3.4/6.2/8.1.1/9.1 R5). Текст 4.3.4 и R5 необходимо синхронизировать с выбранным вариантом.

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 3. 🔴 HIGH — `5.2 coach_settings / 4.5.2 / 4.1.3`
*Свойство:* Завершённость (Completeness)

**Нарушение.** Подтверждено. В 5.2 поле price_per_visit | numeric(10,2) задано без DEFAULT и без указания NOT NULL/nullable. В 4.1.3 (создание тренера админом) описаны только createUser и назначение роли coach в profiles; нигде не сказано, что строка coach_settings создаётся при создании тренера и с каким значением цены. Формула 4.5.3 = COUNT(paid, payment_settled_at IS NULL) × coach_settings.price_per_visit. Если строки coach_settings нет или price_per_visit = NULL, результат NULL/неопределён. Частично смягчает то, что show_payment_due имеет default false (т.е. при наличии строки с дефолтами попап 4.5.5 не покажется, т.к. требует show_payment_due=true И сумма>0), но это работает только если строка реально создаётся с дефолтами — а это и не описано. Кейс «есть paid-визит, но цена не задана» остаётся без определённого поведения. Реальный пробел инициализации.

**Исправление.** В 4.1.3 явно зафиксировать создание строки coach_settings при создании тренера (и в RPC создания тренера). В 5.2 задать price_per_visit numeric(10,2) NOT NULL DEFAULT 0 (или NULL с явной семантикой). Определить поведение расчёта/попапа при price=0/не задана: при price=0 сумма к оплате = 0 → попап и строка «к оплате» не показываются (согласованно с 4.5.3/4.5.5, где условие сумма>0). Опционально: при наличии неоплаченных paid-визитов и неустановленной цене показывать тренеру предупреждение «задайте цену».

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 4. 🔴 HIGH — `4.4.3 / 5.7 / 6.2`
*Свойство:* Завершённость (Completeness)

**Нарушение.** Подтверждено. Для чек-ина в 6.2 детально описана транзакционная RPC (SECURITY DEFINER, одна транзакция: upsert coach_athlete, init memberships, проверка активной сессии, INSERT visit, UPDATE memberships + запись в ledger). Для ручного начисления (4.4.3, reason='grant' в 5.7) механизм НЕ определён: 6.2 RPC покрывает только чек-ин и не упоминает grant. В 7.1 упомянуто «Запись — только через RPC чек-ина/начисления (тренер/админ)» — т.е. RPC начисления подразумевается, но нигде не специфицирована: не сказано про атомарность UPDATE memberships.remaining_visits += N вместе с INSERT membership_ledger(delta=+N, reason='grant'), не заданы ограничения на N (целое, N>0, верхняя граница), и нет явной проверки активной связи coach_athlete.removed_at IS NULL именно для операции начисления (5.3/4.4.4 говорят о потере управления при мягком удалении, но как декларацию, а не как явную проверку в операции). Упомянутый, но неопределённый механизм — реальный пробел.

**Исправление.** Добавить в 6.2 подпункт «Транзакционное начисление абонемента» по аналогии с чек-ином: RPC plpgsql SECURITY DEFINER, в одной транзакции UPDATE memberships SET remaining_visits = remaining_visits + N + INSERT membership_ledger(delta=+N, reason='grant', created_by). Задать валидацию N (целое, N>0, опц. верхняя граница) и явную проверку EXISTS активной связи (coach_id=auth.uid(), athlete_id, removed_at IS NULL) с отказом при мягко удалённой/отсутствующей связи. Зафиксировать инициализацию строки memberships при отсутствии.

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 5. 🔴 HIGH — `4.2.3 / 6.2 (резолв токена)`
*Свойство:* Завершённость (Completeness)

**Нарушение.** Подтверждено частично, но как реальный пробел. 4.2.3 описывает только happy-path: считывание токена → резолв → проверка прав → диалог чек-ина. Негативные ветки не закрыты: (1) токен не найден/просрочен/не bcoach-формат — нет UX; (2) QR принадлежит не-athlete/удалённому аккаунту — нет обработки; (4) повтор уже обработанного скана — нет; сетевые ошибки RPC — нет. Смягчающие факторы (отмечаю для точности): HTTPS-требование явно зафиксировано (4.2.3, 7.6, «Требуется HTTPS»), а ручной ввод токена как фолбэк при недоступной камере есть в 4.2.3 и 8.1.1 (но опционально). Тем не менее обработка невалидного/ненайденного/чужого токена и повторного скана отсутствует полностью. Учитывая безопасность (анти-энумерация токенов — 6.2, R3), отсутствие определённого сообщения об ошибке — реальный пробел. Высокий severity оправдан, т.к. напрямую влияет на основной поток работы тренера.

**Исправление.** Добавить в 4.2.3 раздел обработки ошибок сканирования: невалидный/ненайденный/не-bcoach токен → нейтральное сообщение «QR не распознан» без раскрытия существования аккаунта (согласовать с анти-энумерацией 6.2/R3); QR указывает на не-athlete или удалённый аккаунт → отказ с тем же нейтральным сообщением; повторный скан при активной сессии — переиспользовать правило 4.3.1 («тренировка уже идёт»), явно сослаться; сетевая ошибка RPC → сообщение и повтор. Отказ камеры/не-HTTPS уже частично покрыты (HTTPS обязателен + опц. ручной ввод) — достаточно явно связать их с UX-сообщением.

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 6. 🔴 HIGH — `4.8.5 (п.4), R2`
*Свойство:* Недвусмысленность (Unambiguousness)

**Нарушение.** Внутреннее противоречие в самом тексте: п.4 4.8.5 требует «|hue − targetHue| ≤ ΔH (фиксированный порог, напр. 15–25°) и saturation ≥ Smin и value ≥ Vmin», а строкой ниже и в R2 утверждается, что «Пороги ΔH/Smin/Vmin — фиксированные внутренние константы реализации». При этом ΔH дан как диапазон-пример «15–25°», а Smin и Vmin не имеют вообще никаких числовых значений. Назвать величины «фиксированными константами» и одновременно не задать их — прямое нарушение недвусмысленности: поведение функции color-splash недетерминировано и непроверяемо. Подтверждаю как high.

**Исправление.** Указать точные константы в 4.8.5 п.4 (и сослаться на них в R2), например: «ΔH = 20°, Smin = 0.25 (шкала 0–1), Vmin = 0.20». Если значения подбираются эмпирически — записать как «значения по умолчанию: ΔH=20°, Smin=0.25, Vmin=0.20; подлежат фиксации до релиза Фазы 2», но в любом случае исключить формулировку-пример с диапазоном «15–25°» и проставить числа для Smin/Vmin.

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 7. 🔴 HIGH — `Раздел 3 (User Stories A1-A6, T1-T10, U1-U8) ↔ Раздел 4 (Функциональные требования)`
*Свойство:* Прослеживаемость (Traceability)

**Нарушение.** Подтверждено фактической проверкой. Grep по ID историй (A1..U8) вне раздела 3 даёт пустой результат: ни одна User Story не ссылается на реализующее ФТ, ни одно ФТ не ссылается на историю. При этом спека в остальном плотно перекрёстно ссылается (ФТ↔ФТ↔модель данных: 4.3.1→5.5/6.2, 4.5.3→4.3.2, 5.5→4.3.1 и т.д.), поэтому именно слой US↔FR — единственный полностью оторванный, что и есть ядро прослеживаемости 'пользовательская потребность → требование'. Раздел 9.2 закрывает отдельные открытые вопросы, но это не трассировка историй. Реальный пробел: невозможно доказать покрытие историй и выявить осиротевшие ФТ.

**Исправление.** Добавить двунаправленную трассировку US↔FR. Минимально: к каждой User Story приписать перечень реализующих ФТ (напр. 'T3 → 4.3.1; T4 → 4.3.8; T8 → 4.4.3; U8 → 4.5.5/4.6.3'), а в подпунктах ФТ указать покрываемые истории. Предпочтительно — вынести отдельную матрицу трассируемости US↔FR в приложение (таблица: ID истории | реализующие ФТ | примечание), чтобы автоматически выявлять истории без ФТ и ФТ без истории.

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 8. 🔴 HIGH — `Весь документ — отсутствие раздела приёмки/верификации (требование → проверка)`
*Свойство:* Прослеживаемость (Traceability)

**Нарушение.** Подтверждено: grep по 'приёмоч|acceptance|тест-кейс|верификац|критери.*приёмк|test case' по всему документу даёт ноль совпадений. Раздел 9 содержит только риски (9.1) и открытые вопросы (9.2), без критериев приёмки или тест-кейсов. Это реальный разрыв связи 'требование → способ верификации': ни одно нормативное правило (одна активная сессия на пару, списание не ниже 0, расчёт суммы, закрытие напоминания) не сопоставлено с измеримым критерием выполнения, поэтому матрицу покрытия тестами построить нельзя. Важная оговорка: многие правила сформулированы достаточно конкретно (формулы, CHECK >= 0, частичный unique-индекс), но это спецификация поведения, а не критерии приёмки — отдельного слоя верификации в документе нет.

**Исправление.** Добавить раздел 'Критерии приёмки / Верификация' с явной привязкой к ID требований. Для ключевых ФТ задать измеримые проверки, например: 4.3.1 — 'при повторном скане активной пары новый визит НЕ создаётся, абонемент НЕ списывается, показывается существующая сессия' (тест на нарушение unique-индекса); 4.4.2 — 'списание при остатке 0 оставляет remaining_visits = 0 и membership_decremented = false'; 4.5.3 — 'сумма = COUNT(paid, payment_settled_at IS NULL) × price_per_visit, membership-визиты исключены'; 4.5.4/4.6.3 — 'закрытие напоминания проставляет payment_settled_at всем неоплаченным paid-визитам пары в одной транзакции, сумма становится 0, напоминание исчезает'. Каждый критерий снабдить ссылкой на номер ФТ.

**Статус:** ✅ применено в SPEC v1.1 + миграциях

### 9. 🟠 MEDIUM — `4.3.1 (буллет «Правило одной активной сессии на пару»)`
*Свойство:* Атомарность/единичность (Atomicity)

**Нарушение.** Подтверждено: буллет совмещает три разнослойных утверждения — (1) бэкенд-правило «новый визит НЕ создаётся и абонемент НЕ списывается» при активной сессии; (2) UI-требование «показывается существующая активная сессия (сообщение «тренировка уже идёт»)»; (3) требование к схеме БД «частичным уникальным индексом unique(coach_id, athlete_id) where ended_at is null».
